# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

`AGENTS.md` is generated by `next dev` and rewritten between its markers. Don't edit inside the markers; content outside them is preserved. Keep shared, tool-agnostic notes short there and put detailed project rules in this file.

## Working agreement

Before any significant change (new feature, new route, new dependency, config change, or a refactor touching more than a couple of files), propose a short plan first: what changes, which files, which Next.js docs were checked, and the alternatives that were rejected. Wait for approval. Small, local fixes don't need a plan.

Don't add dependencies without asking. Prefer what Next.js, React, and the platform already provide.

## Commands

Use the Node.js version in `.nvmrc` (`nvm use`); CI reads the same file. `engines` in `package.json` only sets the minimum Next.js supports.

- `npm run dev` — dev server (Turbopack) at http://localhost:3000; set `PORT` in the shell for another port (`PORT=3001 npm run dev`; Next.js doesn't read it from `.env`)
- `npm run lint` — ESLint 10 flat config (`eslint-config-next` core-web-vitals + typescript); checks the whole project
- `npm run format` — format the whole project with Prettier (writes files); `npm run format:check` only reports unformatted files, as CI does
- `npm run build` — production build; this is also the type check (there is no separate `tsc` script)
- `npm run start` — serves the production build (run `npm run build` first)
- `npm run test:unit` — Vitest unit and component tests (`src/**/*.test.ts(x)`), run once
  - One file: `npm run test:unit -- src/lib/errors.test.ts`
  - By test name: `npm run test:unit -- -t "getErrorDigest"`
  - Watch mode while developing: `npm run test:unit:watch` (don't use it in scripts or agents; it never exits)
- `npm run test:e2e` — Playwright E2E tests (Chromium) in `tests/e2e/`; starts `npm run dev` itself, or reuses a server already on port 3000, or on `PORT` when set (see [Testing](#testing))
  - One file: `npm run test:e2e -- tests/e2e/homepage.spec.ts`
  - By test name: `npm run test:e2e -- -g "homepage loads"`
  - Debugging: append `-- --ui` or `-- --headed`; open the last HTML report with `npx playwright show-report`

**Before calling work done:** run `npm run format`, then `npm run lint`, `npm run test:unit`, and `npm run build`, and all must pass. For UI or route changes, also run `npm run test:e2e` and check the page in the running dev server with a browser tool, preferably Playwright MCP (see [MCP tools](#mcp-tools)).

## Stack and non-default config

Next.js 16.4 (App Router), React 19.3, TypeScript strict, Tailwind CSS v4. `next.config.ts` turns on features that change how code is written. Read the matching docs in `node_modules/next/dist/docs/01-app/` before working on data, caching, or navigation:

- **`cacheComponents: true`**: data fetching is dynamic by default; caching is opt-in with `use cache` + `cacheLife`, and uncached request-time data goes inside `<Suspense>`. The route segment configs `dynamic`, `revalidate`, and `fetchCache` error under this model, and the `runtime` segment config is unsupported. Don't call `Date.now()`, `Math.random()`, etc. in the prerendered shell. See `01-getting-started/08-caching.md` and `02-guides/migrating-to-cache-components.md`.
- **`partialPrefetching: true`**: requires `cacheComponents`. Links prefetch the route's static shell by default; `<Link prefetch={true}>` also fetches URL-dependent content. See `02-guides/optimizing-prefetching.md`.
- **`reactCompiler: true`** (with `babel-plugin-react-compiler`): reduces the need for manual memoization. Don't add `useMemo`/`useCallback`/`memo` by default.
- **Tailwind via Turbopack loader**: `turbopack.rules` runs `*.css` through `@tailwindcss/turbopack`; there is no `postcss.config`. The Next.js CSS docs (`01-getting-started/11-css.md`) describe a `@tailwindcss/postcss` setup instead. This project doesn't use it, so don't follow those steps without discussing it first.

## Folder organization

```
src/
  app/          routes only: page.tsx, layout.tsx, loading.tsx, error.tsx, not-found.tsx, route.ts
                route-private pieces go in _components/ next to the route
  components/   shared UI used by more than one route
  lib/          non-UI logic: data access, validation, utilities (no JSX)
public/         static assets
```

Import through the `@/*` alias (maps to `src/*`), not long relative paths.

The root `not-found.tsx`, `error.tsx`, `global-error.tsx`, and the shared components in `src/components/` are meant to stay.

There is intentionally no root `loading.tsx`: it would wrap every page in one generic fallback and hide missing `<Suspense>` boundaries that Cache Components reports at build time. Add `loading.tsx` per segment where a page reads request-time data.

## TypeScript and React

- Server Components are the default. Add `"use client"` only for state, effects, event handlers, or browser APIs, and put it on the smallest leaf component possible.
- Type route props with Next's generated global helpers (`PageProps<"/path">`, `LayoutProps<"/path">`). Note that `params`/`searchParams` are Promises.
- No `any`. Use `unknown` and narrow it. Prefer `type` imports (`import type { … }`).
- Named exports for components in `components/`. Default exports only where Next requires them (`page`, `layout`, etc.).
- Keep data fetching and mutations out of presentational components: fetch in Server Components or `lib/`, and mutate through Server Actions.

## Styling

- Prettier owns code formatting and Tailwind class order (`prettier.config.mjs`, with `prettier-plugin-tailwindcss`). Don't format by hand or argue style in review; run `npm run format`. ESLint's formatting rules are turned off by `eslint-config-prettier`. The plugin sorts classes in `className` attributes only, not in string constants such as `buttonClasses`.
- Reformatting commits that touch many files go in a commit of their own, added to `.git-blame-ignore-revs`. Merge those PRs with a merge commit, not a squash, so the listed SHA survives.
- Tailwind utility classes in JSX. Avoid new CSS files and inline `style` except for truly dynamic values.
- Design tokens live in `src/app/globals.css`: CSS variables on `:root` (light and dark), exposed through `@theme inline`. Add new colors and fonts there instead of hard-coding hex values.
- Support dark mode with `dark:` variants, matching the existing `prefers-color-scheme` setup.
- When the same class combination repeats, extract a component rather than using `@apply`.

## Error handling and validation

- Use the route-level file conventions: `error.tsx` (a client component that recovers with `retry()`, not the older `reset()`, which re-renders without re-fetching), `not-found.tsx` with `notFound()`, and `global-error.tsx` for the root. See `01-getting-started/10-error-handling.md`.
- For expected errors in Server Actions (such as validation failures), return them as values for the form to display. Don't throw.
- Validate all external input (form data, params, searchParams, route handler bodies) on the server, even if the client also validates. No validation library is installed yet. Ask before adding one.

## Testing

For every new feature, identify the tests it needs and include them in the plan:

- **Unit tests** for business logic: pure functions and validation in `lib/`. This is the first priority.
- **Integration tests** for important workflows: Server Actions, Route Handlers, and components working together.
- **Browser (E2E) tests** for critical user journeys. Test async Server Components this way, since unit-test tooling doesn't fully support them (per `02-guides/testing/index.md`).

Automated browser tests use Playwright Test (`@playwright/test`) and run with `npm run test:e2e`; see `playwright.config.ts`. It is the repeatable browser test tool. The Playwright MCP server is separate: it's for interactive checks, not for tests.

### Unit and component conventions (Vitest)

Unit and component tests use Vitest with Testing Library; see `vitest.config.mts` and `02-guides/testing/vitest.md`. Ask before adding test dependencies (for example `@testing-library/jest-dom` or `@testing-library/user-event`).

- Colocate tests next to the code: `src/lib/errors.ts` → `src/lib/errors.test.ts`. Only `src/**/*.test.ts(x)` is collected, so Playwright's `tests/e2e/*.spec.ts` never runs under Vitest.
- The file extension picks the environment: `*.test.ts` runs in Node (the `unit` project) and `*.test.tsx` runs in jsdom (the `component` project, with `vitest.setup.ts`).
- Globals are off: import `describe`, `test`, `expect`, and `vi` from `vitest`. `vitest.setup.ts` handles Testing Library cleanup.
- Query components by role, as in the E2E tests (`screen.getByRole`).
- Don't unit test async Server Components; Vitest can't render them. Cover them with E2E tests, and move their logic into `lib/` functions that can be unit tested.

### E2E conventions (Playwright)

- Specs go in `tests/e2e/` as `*.spec.ts`, one file per page or user journey.
- Navigate with relative URLs (`page.goto("/")`); `baseURL` is `http://localhost:3000`, or the `PORT` env var's port when set.
- Locate elements the way users find them, with visibility-aware locators first: `getByRole`, then `getByLabel` or `getByPlaceholder`. Avoid CSS classes and DOM structure, which change with styling.
- With Cache Components, routes you navigate away from stay in the DOM, hidden with `display: none` (React `<Activity>`), so a query that ignores visibility can match the previous page's content. Use `getByText` or `locator()` only when the match is known to be visible and unique: scope it to a visible container or add `.filter({ visible: true })`. Each locator must match exactly the one visible element you intend. `toBeVisible()` checks visibility but doesn't resolve ambiguous matches, so narrow the locator rather than reaching for `.first()` or `.nth()`. See `02-guides/preserving-ui-state.md` (Testing).
- Use web-first assertions (`await expect(locator).toBeVisible()`), which retry. Never use `page.waitForTimeout` or fixed sleeps.
- Keep tests independent: no shared state or required order between tests.
- Only Chromium is configured. Ask before adding browsers (`npx playwright install` downloads them) or Playwright plugins such as `@next/playwright`.
- Locally, tests run against the dev server. In CI (`CI=true`), `webServer` runs `npm run start` against the production build instead, so run `npm run build` first. To reproduce a CI run locally: `npm run build && CI=true npm run test:e2e`.
- `webServer` reuses whatever is listening on its port outside CI. If a different app or another checkout of this repo is running there, stop it first or use another port (`PORT=3001 npm run test:e2e`).
- Reports and artifacts (`playwright-report/`, `test-results/`, and Playwright MCP output in `.playwright-mcp/`) are gitignored. Don't commit them.

## Security and environment variables

- Secrets go in `.env.local` (already gitignored by `.env*`). Never commit them or print them in logs.
- Only `NEXT_PUBLIC_`-prefixed variables reach the browser. Never put a secret behind that prefix. See `02-guides/environment-variables.md`.
- Do secret-dependent work only in server code. Treat every Server Action and Route Handler as a public endpoint: check authorization inside it. See `02-guides/data-security.md`.
- If the project starts needing an env var, add a committed `.env.example` with names only and no values.

## Git workflow

- `main` is the default branch. Make feature and configuration changes on a short-lived branch (`feat/…`, `fix/…`, `chore/…`, `docs/…`) and merge them through a pull request. Push directly to `main` only when the user explicitly asks.
- Conventional Commits: `feat: …`, `fix: …`, `refactor: …`, `chore: …`, `docs: …`. Imperative mood, subject ≤ 72 chars.
- Lint and build must pass before committing. Commit, push, and open pull requests only when asked.
- CI (`.github/workflows/ci.yml`) runs `npm ci`, the format check, lint, unit tests, build, and Chromium E2E tests on pull requests into `main` and on pushes to `main`. It must pass before a pull request is merged. Pin third-party actions to full commit SHAs with the version in a comment.
- Dependabot (`.github/dependabot.yml`) opens grouped update PRs for npm and GitHub Actions every Sunday, after a 7-day cooldown (30 days for majors). Merge them only when CI passes, and read the changelog for any major update. For a Next.js upgrade, read `01-getting-started/18-upgrading.md` and the bundled docs from the new version before changing code. Don't push commits to a Dependabot branch; comment `@dependabot rebase` or `@dependabot recreate` instead. `@types/node` majors are ignored on purpose: bump them together with `.nvmrc`. Prettier updates have their own group; if one fails the format check, close it and redo the update with `npm run format` in a normal `chore/` PR.
- When committing (only when asked), include any `AGENTS.md` changes `next dev` made, so the tree stays clean.
- Worktrees (`claude --worktree`, or isolated subagents) live in `.claude/worktrees/`, which is gitignored and skipped by ESLint. In a worktree, run `npm install` first, and use a port other than the main checkout's for `dev` and `test:e2e` (see the README's worktree section). `.worktreeinclude` copies `.env*` files in.

## MCP tools

No MCP servers are configured in the repo (no `.mcp.json`); each developer connects their own, and none is required to contribute. Tool names and availability depend on the session and client, so check what's actually loaded rather than assuming. Connected in the current setup:

- **Playwright MCP** (`@playwright/mcp`, added at Claude Code's local scope): browser navigation, page inspection (accessibility snapshots, console messages, network requests), screenshots, and interaction (clicking, typing, filling forms). When available, it's the preferred tool for interactive browser verification of UI changes against `npm run dev`, including dark mode and narrow widths. Repeatable checks belong in Playwright Test specs instead (see [Testing](#testing)). Its snapshots and logs go to `.playwright-mcp/`. To connect it: `claude mcp add playwright -- npx -y @playwright/mcp@latest`.
- **Claude Docs** (claude.ai connector): only when the user asks for a shareable document, not for code or repo docs.
- **IDE diagnostics** (through the editor's MCP integration, such as the VS Code extension): a quick check for type and lint errors in edited files. It doesn't replace `npm run lint` and `npm run build`.

Other browser tools (Claude in Chrome, the desktop app's built-in browser) also work for interactive checks; they have to be turned on through their skills. If no browser tool is loaded, `curl` against the dev server can confirm HTTP status and returned HTML, but it can't show how the page looks or behaves. In that case, report that visual and interaction checks weren't done and ask the user to check the page; never report them as passed.

Don't use MCP tools to look up Next.js APIs. The bundled docs in `node_modules/next/dist/docs/` match the installed version.

## Documentation lookups

For Next.js, always use the bundled docs in `node_modules/next/dist/docs/` (see above), never Context7.

For other libraries, frameworks, SDKs, APIs, CLI tools, or cloud services (including Git/GitHub CLI, GitHub Actions, Node.js, Cloudflare R2), use the Context7 MCP server when it's connected, without being asked. It's optional, like every MCP server here:

1. `resolve-library-id` to find the library ID (skip if given an `/org/project` ID).
2. `query-docs` with that ID, one concept per query.
3. Answer from the fetched docs rather than from memory.

Skip Context7 for general programming concepts or edits that don't depend on a library API. If it isn't connected, use the library's official docs.
